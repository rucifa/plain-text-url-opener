## Scope

v1.0.12 implements the Fixture v1.4 Defanged URL interaction specification without changing the parser's default blocked classification:

1. Ordinary double-click on a Defanged URL remains fail closed.
2. `Ctrl + Shift + double-click` explicitly lifts only the `defanged` block; `Alt` must not be present.
3. The restored URL is revalidated through the normal explicit HTTP(S) normalization / safety path before navigation.
4. User Info / IDN warning properties from revalidation are preserved.
5. The override uses the same open mode as ordinary double-click, so the `Shift` inside the override chord does not reverse the open mode.
6. `Ctrl` alone and `Shift` alone do not grant the override.

Firefox can create a multi-range / cross-container native selection when `Ctrl` participates in a double-click. The compatibility fallback uses the double-click pointer position only when native same-TextNode selection is unavailable, then accepts the fallback solely if the clicked candidate is already parser-classified as `blocked` with `reason === 'defanged'`. It does not create a generic Ctrl force-open path.

## Firefox compatibility diagnosis

A native Firefox probe confirmed the browser-level difference that initially blocked the new gesture:

- ordinary double-click / Shift + double-click: one same-TextNode range
- Ctrl + double-click / Ctrl + Shift + double-click: three selection ranges, with the first range crossing Element → TextNode

The final implementation adds the narrow pointer/caret fallback described above rather than weakening the global single-TextNode rule.

## Modifier security probes

The following cases were exercised on both Chromium and Firefox and all remained non-navigable:

- Defanged URL + `Ctrl + Shift + Alt`
- `javascript:https://...` + `Ctrl + Shift`
- `data:...https://...` + `Ctrl + Shift`
- `file://https://...` + `Ctrl + Shift`
- `ftp://https://...` + `Ctrl + Shift`
- `mailto:https://...` + `Ctrl + Shift`

Result: **PASS on both browsers**.

## Harness classification record

An early full-regression run reported failures for the existing multi-URL cases. Diagnosis showed a **test-harness failure**, not a product regression: multi-URL specs did not define the new `expectNavigation` field, while the adapted harness tested strict `=== null` and therefore treated the field's `undefined` value as an explicit no-open expectation. The harness was corrected to use the existing behavior when the field is nullish; subsequent Chromium and Firefox full runs passed 178 / 178.
