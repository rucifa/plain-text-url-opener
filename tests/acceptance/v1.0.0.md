## Blocker found before release

### Reproducible wrong-target fallback

RC4 could incorrectly recover a later bare-domain fragment from inside the same malformed scheme-like token.

Examples:

- `https://trusted.com%40evil.org` → incorrectly detected `40evil.org`
- `https://trusted.com|evil.org` → incorrectly detected `evil.org`
- `https://trusted.com^evil.org` → incorrectly detected `evil.org`

This met the Handoff blocker definition because it was a reproducible wrong target / clear false positive.

### Fix

A narrow boundary rule was added:

- bare/www candidates are rejected when they are nested later inside the same non-whitespace token that already contains a valid `scheme://` prefix.
- no new URL type, UI, setting, protocol, or behavior was added.

Regression coverage was added for all three malformed inputs plus a valid percent-encoded hostname case.

### Browser sandbox note

The test environment blocks external HTTP(S) navigation at the browser/network policy layer. Therefore final cross-origin network completion itself could not be asserted. The acceptance test instead separately verified:

1. a real Chromium popup is created by the double-click user gesture; and
2. the actual script calls `window.open('about:blank', '_blank')`, nulls `opener`, and sends the exact detected HTTP(S) target to the popup navigation sink.

This is an environment limitation, not a script failure.
