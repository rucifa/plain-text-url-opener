## Regression found during full Fixture execution

The original v1.0.5 hardening candidate passed its focused 30 parser checks and 10 Chromium interaction checks, but full Fixture execution exposed six regressions in pre-existing multilingual-adjacency cases:

- `bare-cyrillic`
- `bare-greek`
- `bare-thai`
- `bare-arabic`
- `bare-hebrew`
- `bare-devanagari`

Representative regression:

```text
example.comРусский
```

Expected:

```text
https://example.com/
```

The Unicode-expanded scheme-less bare-domain matcher consumed the adjacent non-Latin prose as part of the hostname. The resulting full hostname then failed delegated-TLD validation, losing the previously supported `example.com` prefix.

This was classified as an **implementation regression**, not a Fixture error and not a product-specification change.

## Corrective patch

A narrow `trimLikelyAdjacentNonLatinProse()` fallback was added.

The fallback:

1. applies only to scheme-less `bare` / `www` candidates;
2. first preserves a full candidate whenever it already validates as a supported scheme-less domain, protecting valid IDNs;
3. only recovers a shorter prefix when the full candidate fails and the suffix begins with a non-Latin Unicode letter;
4. requires the recovered prefix itself to pass the normal scheme-less-domain validation;
5. preserves the existing conservative Latin adjacency behavior (`example.comFrançais` is not automatically shortened);
6. leaves the pre-existing CJK adjacency logic authoritative for CJK text.

No event handling, UI, navigation, lifecycle, popup, opener-isolation, or background-scanning architecture was changed by this corrective patch.
