## Release-blocking findings fixed

### 1. Quadratic trailing-delimiter trimming

Reproduction:

```text
https://example.com/))))))))))))))))...  (~8 KB of trailing ')')
```

v1.0.1 repeatedly rescanned the candidate while removing unmatched closing delimiters. This produced approximately quadratic worst-case behavior and a visible main-thread stall.

Chromium benchmark from the final pass:

- v1.0.1: ~684.6 ms per ~8 KB pathological candidate (2-run sample; intentionally kept small because the old path is slow)
- v1.0.2: median ~0.8 ms, p95 ~1.1 ms (50 runs)

Fix:

- Count recognized opening/closing delimiters once.
- Trim unmatched trailing closers using the counts instead of repeatedly rescanning the whole string.

Safety check:

- 200,000 randomized trim inputs: old and new trimming results were exactly equivalent.

### 2. Partial bare-domain matches inside malformed hostname-like tokens

Reproducible v1.0.1 examples included:

```text
aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa.com
example.com123
example.co123
x-aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa.com
example.com.123
```

The bounded bare-domain regular expression could start or stop inside a larger malformed ASCII hostname-like token and recover a shorter apparently valid domain.

Fix:

- Strengthen bare-domain left/right boundary validation.
- Preserve existing punctuation behavior such as `-example.com`.
- Preserve existing CJK/Unicode behavior.
- Do not broaden URL support.

### 3. Huge-TextNode scan-window clipping could create a wrong target

The architecture intentionally scans only approximately ±4096 characters around the interaction point when a TextNode exceeds 8192 characters.

Reproduction pattern:

```text
https://host.example/<very long non-whitespace token>...|evil.com|...
```

If the real token started outside the left side of the scan window, v1.0.1 could see only `evil.com` inside the window and treat it as an independent bare domain. The reverse direction could also allow a very long URL to be truncated at the right scan boundary.

Fix:

- Keep the existing bounded-scan architecture.
- If a candidate belongs to a non-whitespace URL token that is clipped by the scan window on either side, reject that candidate rather than guessing.
- Fully contained candidates inside huge TextNodes continue to work.

This intentionally favors a false negative on an extreme >8 KB unbroken token over opening a wrong target.

## Code simplification / maintainability review

Accepted:

- Width normalization is performed once before the quick URL probe instead of being repeated by the probe.
- One redundant `pendingPointerEvent = null` assignment was removed because `resetHoverState()` already performs it.
- The quadratic delimiter implementation was replaced by a linear implementation; this is both simpler in complexity and dramatically faster in the pathological case.

Rejected after testing:

- Removing the pre-normalization bare-domain validation looked redundant, but differential fuzzing showed that it changes semantics for strings beginning with `www.` that were reached through the bare matcher. It was restored.
- More aggressive parser deduplication/refactoring was not accepted where behavioral equivalence could not be demonstrated.

Result: total source size is slightly larger than v1.0.1 because the huge-node clipping guard and boundary checks are explicit. This was preferred over reducing line count at the cost of auditability or behavior changes.

## Chromium performance comparison

Representative final-run figures (milliseconds):

| Case | v1.0.1 median | v1.0.1 p95 | v1.0.2 median | v1.0.2 p95 |
|---|---:|---:|---:|---:|
| ~8 KB normal text | 2.1 | 3.5 | 1.9 | 2.2 |
| ~8 KB dotted pathological input | 3.0 | 3.4 | 2.9 | 3.2 |
| ~8 KB trailing `)` pathological input | ~684.6* | ~684.6* | 0.8 | 1.1 |
| ~7 KB text with explicit URL | 0.2 | 0.3 | 0.2 | 0.3 |
| >8 KB TextNode, contained bare domain | 2.2 | 2.8 | 2.0 | 2.3 |
| >8 KB TextNode, contained explicit URL | 0.2 | 0.4 | 0.1 | 0.3 |

`*` Old pathological closer test used only two measured runs because each run takes hundreds of milliseconds; the figure is for regression magnitude, not statistical precision.

No meaningful performance regression was found in normal or previously hardened cases.

- `@grant none`
- only HTTP/HTTPS `@match`
- no `MutationObserver`
- no `setInterval`
- no `requestAnimationFrame` processing loop
- no `eval()` / `new Function`
- no `innerHTML` sink
- no GM API dependency

## Remaining limitations

No intentionally excluded feature was added during this pass. Existing design limitations remain design limitations rather than release blockers, including cross-TextNode reconstruction, bare IPv4, broad URI schemes, relative paths by default, full PSL embedding, and inaccessible closed Shadow DOM content.
